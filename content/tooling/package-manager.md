A **package manager** installs dependencies, resolves [[semantic-versioning|versions]], writes lockfiles, and runs [[npm-script|scripts]].

Common JavaScript package managers include npm, pnpm, and Yarn.

Lockfiles make installs repeatable. Choose one package manager per project and keep its lockfile committed.

## How it works

Given `package.json`'s declared dependencies, the package manager resolves a full dependency tree — including transitive dependencies — and writes the resolved versions to a lockfile. npm and Yarn Classic flatten this tree into a single `node_modules` directory; pnpm instead stores each package version once in a global content-addressable store and links it into each project via symlinks.

## When to use

npm works with no extra setup and is fine for most single-package projects. pnpm's stricter resolution — a package can only `import` what it explicitly lists as a dependency — catches "phantom dependency" bugs that a flat `node_modules` silently allows, which matters most in monorepos where many packages share a tree.

## Trade-offs

pnpm's strictness and disk savings (one copy of each package version shared across every project on the machine) come at the cost of occasional incompatibility with tools that assume a flat `node_modules` and walk up the tree expecting to find arbitrary packages that aren't their own dependencies.

## Pitfalls

A phantom dependency — importing a package that's installed (because some direct dependency depends on it) but never declared in your own `package.json` — works until that direct dependency removes or updates its own dependency, at which point the import breaks with no warning beforehand. Committing a lockfile generated by a different package manager than the project actually uses (an npm `package-lock.json` alongside a `pnpm-lock.yaml`) creates two sources of truth and inconsistent installs across machines and CI.
